# tonetool

Choir practice tool. Prototype stage: import a MusicXML score, review its structure
(sections, repeats, jumps), and play it in the browser with a per-voice mix (e.g. "alto loud on the
left, everyone else quiet on the right, 80% tempo"), or download the result as MP3 or WAV.

## Design

- **MusicXML is the immutable source for notes.** `piece.json` is the final authority for sections
  and playback order; the importer only *suggests* them (`"source": "auto"`).
- Measures are referenced by 0-based document-order index, never printed number.
- Notes live in the measures, keyed by track: `Measure.voices[track_id]` is a `VoiceMeasure`
  (what that voice sings in that bar; empty if it rests, never missing). `Track` is just id/label/voice kind, so the measure count
  exists in one place; `Piece.voice_measures(track_id)` gives the horizontal view of one voice.
- Sections are named stretches of the *performance*: each holds one or more notated ranges
  (`segments`), and the playback order is generated by playing the sections in order. So the same
  bars can appear in several sections (verse 1 and verse 2), and a section can end in either of
  two voltas. Section data is per-pass, which is where per-verse data such as lyrics lives.
- The **key** (`Piece.key`: tonic such as `Bb` or `F#`, and major or minor) is suggested at import from
  the first key signature. A signature only gives the number of sharps or flats, so between the major
  key and its relative minor the one whose tonic is the lowest note of the last bar wins (major if
  neither). It is only a suggestion; set it in the edit panel.
- **Lyrics** are stored on the notes (`Note.lyrics`: one syllable per MusicXML lyric line), and
  `Section.lyric_number` says which lyric line a section sings. They are separate because a score's
  lyric line is not a verse: the song may sing verse 1 and verse 3 on line 1 in different bars. The
  importer suggests the number by counting passes over the same bars (the second pass over a bar sings
  line 2) and strips verse labels such as `1.` from the text; edit it in the JSON, with
  `"source": "user"`, if the guess is wrong. Because a section has one lyric line, give each verse its
  own section. Syllables are joined into words by the `begin`/`middle` flags only, since exporters
  are inconsistent about the rest.
- Ties are stored as a flag on the continuing note (`tied`), not merged at import. The frontend
  timeline resolves them in *performed* order: a `tied` note extends the held note of the same pitch if one
  ends exactly where it starts; otherwise (a jump or loop landed mid-tie) it sounds without an attack.
- `models.py` (Piece, Track, Section, PlaybackOrder) · `structure.py` (lxml: repeats, endings,
  `<sound>` jumps, rehearsal marks → suggestions) · `importer.py` (music21 notes + structure →
  Piece) · `api/` (FastAPI: serves stored pieces) · `cli.py` (thin wrapper).
- **The backend is storage and import only.** Everything derived lives in `frontend/src/music/`
  (unrolling sections into performed time, tie resolution, tempo) and `frontend/src/audio/` and
  `frontend/src/export/` (Web Audio playback and offline rendering). There is one implementation
  of that logic. The original Python timeline and renderer were removed.

## Usage

```bash
uv sync
uv run tonetool import examples/endings.musicxml      # -> examples/endings.piece.json
uv run tonetool show examples/endings.piece.json      # tracks, sections, order, warnings
uv run tonetool import SCORE.xml -o PIECE.piece.json --keep-sections   # refresh notes and lyrics, keep your sections
uv run pytest
```

To correct a wrong suggestion, edit `sections` in the JSON (their order *is* the playback order)
and set `"source": "user"`. Ranges are inclusive, 0-based measure indices (bar 1 = 0):

```json
"sections": [
  {"id": "verse1", "name": "Verse 1", "segments": [{"start": 0,  "end": 11}], "source": "user"},
  {"id": "verse2", "name": "Verse 2", "segments": [{"start": 0,  "end": 11}], "source": "user"},
  {"id": "verse3", "name": "Verse 3", "segments": [{"start": 12, "end": 23}], "source": "user"}
]
```

Tempo is stored as `"tempo"` (quarter-note BPM) on the measure where a tempo mark sits, and is
`null` elsewhere. A mark applies to its measure and the ones after it **in notated order**, until
the next mark. To change the tempo of the whole piece, edit `tempo` on the first measure only; to
add a change, put a value on the measure where it starts. The player's tempo slider scales the result.

## Web player (draft)

The backend only stores and serves pieces; the browser unrolls the sections (`frontend/src/music/timeline.ts`)
and synthesises the audio with Web Audio, so volume, pan and instrument per
voice change instantly. Pick a piece, press play, or click a section to start from there. The lyrics of the voice you follow show
the previous, the current (with the sung syllable highlighted) and the next line; click any syllable to jump to it.

The **piano roll** shows the piece in performed order (time to the right, pitch up) with each note coloured
by its place in the key, from red *do* (the tonic) to purple *ti*. Colours depend only on the interval
from the tonic, so major and minor keys share them: a lowered step is the same hue but darker (*mi* and
*me* are one colour, *mi* the brighter) and notes outside the key's scale are outlined. Click to jump,
hide voices with the chips, zoom, and let it follow the playhead. Without a key the notes are one colour;
set the key in the edit panel.

```bash
cp tonetool.example.toml tonetool.toml   # [[pieces]] entries link ids to piece.json files
uv run tonetool serve                    # API on :8000 (--config / TONETOOL_CONFIG to choose a file)
cd frontend && npm install && npm run dev   # UI on :5173, proxies /api to :8000
npm test                                 # timeline + cursor tests
npm run gen:types                        # regenerate src/api/schema.d.ts after changing the pydantic models
```

**Importing and editing in the app.** Set `library = "library"` in `tonetool.toml` (see
`tonetool.example.toml`) and use *Import score…* to upload a MusicXML file (`.musicxml`, `.xml`, `.mxl`).
Each import is stored in `<library>/<id>/` with the original score and `piece.json`; the id is made
from the title and numbered if taken. *Edit* opens a panel for the title, the tonal key, the voice labels and kinds
(S/A/T/B), and the sections: name, bar ranges (typed as `1-12, 15`, counting from 1), lyric line,
order, add and remove. Changes can be heard and seen at once; *Save* sends them to the server,
which checks them with the same rules as `piece.json` and answers with what is wrong if they do not
hold. Sections you change are marked `user`. *Replace score…* re-imports the piece from a new export
but keeps its sections, title and voice labels, and needs the same number of bars and parts.
*Delete* moves a library piece to `<library>/.trash`. Pieces linked with `[[pieces]]` can be edited
(in place, the previous file is kept as `piece.json.bak`) but not deleted. Notes, lyrics text and
tempo marks always come from the score and are not editable.

The API behind it: `POST /api/pieces` (upload), `PUT /api/pieces/{id}` (edit), `POST
/api/pieces/{id}/score` (replace score), `DELETE /api/pieces/{id}`. There is no login, so keep the
server on localhost (its default) and do not expose it.

**Instruments** (`frontend/src/audio/instruments/`) are synthesised from standard Web Audio nodes, so live
playback and the offline export use the same code: *Choir ooh* and *aah* (detuned sawtooths through formant
filters, vibrato that sets in after a straight start, a little breath noise; the first formant follows
high notes), *Strings*, *Organ*, *Flute* (breath noise, vibrato) and *Soft piano* (slightly sharp upper
partials that decay faster than the low ones, a hammer thump). Their levels are calibrated to be about
equally loud. The tests model each instrument's node graph and spectrum rather than render audio, so they
catch clicks, leaks, loudness mismatches and misplaced formants, but not whether it sounds good; that
needs listening.

If synthesis is not good enough, real samples fit behind the same `Instrument` interface:
1. a **SoundFont** synth (e.g. `spessasynth_lib`) with a permissively licensed SF2 (GeneralUser GS,
   FluidR3) that has choir and voice patches. 30 MB or more, lazy-loaded; check the licence and that
   offline export works with an AudioWorklet synth;
2. a **sampler** (Tone.js `Sampler`, WebAudioFont) with a small multisampled set: lighter, but choir
   vowels need good samples and licences vary;
3. **your own recordings**: sustained vowels every few semitones for each voice type. Best for a choir
   app, and the most work.

Notes: browsers only start audio after a click; on iPhones the hardware silent switch also mutes
Web Audio. Live playback is scaled by 1/sqrt(voices) for headroom; exports are not, and are only
scaled down if they would clip.

**Downloads.** *Current mix* renders the piece with the mixer and tempo as set. *Practice set (zip)*
ignores them and always uses the defaults. It contains:

- `<title>_tutti`: all voices together
- `<title>_<voice>_solo`: only that voice plays
- `<title>_<voice>_prominent`: that voice at full volume, the others at 0.3 combined (each of the
  n others scaled by 1/sqrt(n), because voices add up)
- `<title>_<voice>_stereo`: that voice fully left, all the others fully right, balanced so both ears
  are about equally loud (use headphones)

All files have the same length, so they stay in sync when you switch between them. A piece with a
single voice only gets the tutti file.

## Known limits

- Audio is a plain additive-synth tone (no soundfont yet); the instruments are small oscillator presets.
- There is no count-in or metronome in the web player yet (the removed Python renderer had both).
- A tempo mark counts from the start of the measure it sits in (mid-measure changes are
  approximated that way).
- Editing in the app covers sections, title and voice labels; tempo marks and lyric text cannot be
  edited, and saves are last-write-wins (no protection against two browser tabs editing at once).
- Lyric line breaks are guessed (after . ! ? and where the voice rests for a beat), since MusicXML
  has none. Only one lyric line per section; elisions and extenders (melismas) are not shown.
- Text-only jumps ("D.S. al Coda" without `<sound>` attributes) are warned about, not followed.
- Tests use synthetic scores from `tests/scorebuilder.py`; real exporter output (MuseScore, etc.)
  still needs to be tried.
